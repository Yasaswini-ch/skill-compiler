# Skill Compiler + Gemma Fail Museum: write-up

## Problem

Agent skills are long instruction files. Small open models often skip a step, merge two steps, forget an earlier result or break a rule, and nothing flags it. There is also no shared record of how they fail.

## Approach

The harness splits a `SKILL.md` into ordered steps, runs one step at a time with the results it depends on, checks each output (format and rules first, then a model verifier that answers PASS or FAIL), and retries with the checker's note as feedback. A step that still fails after the retries is recorded as `fail` and the run continues. Every run is written to a `trace.json`.

Around the harness: a benchmark that scores plain vs harness with programmatic checks, a labelled failure dataset (the Fail Museum), a no-AI skill linter that estimates risk for small models, and web pages to show it all.

## How we measured

- 10 hand-written tasks, each a skill, an input and 4 to 7 checks a script can verify. The tasks were frozen before the first plain run (one over-strict check was fixed afterwards and disclosed in `benchmark/FROZEN.md`). Separately, 30 harder variants were generated by the model: 25 passed schema validation, 12 of those were hand-reviewed and 5 of the 12 were dropped. They are a supplementary set and are not in the official numbers.
- Plain = the whole skill and input in one prompt. Harness = the steps above. Same model (`gemma-4-26b-a4b-it`), same scorer, same thinking setting (the default, MINIMAL).
- Harness verifier: ON. No response cache.
- Failures are labelled by rule, then reviewed by hand.

## Results

From `benchmark/output/results.json` (official run) and `benchmark/RESULTS_NOTE.md`.

| | Passed |
|---|---|
| Plain | 7 / 10 |
| Harness | 9 / 10 |

Two repeat runs with the same settings gave the same pass counts, and every task had the same result in all three runs.

Overhead: about 16x the calls and about 14x the time (calls 16.2 against 1.0 per task; 49.9 s against 3.6 s).

Failure types the harness fixed: running arithmetic across steps (t04, t05) and a fixed output table (t08). Failure types it did not fix: t03, where the final step changed the type of a value (`no` became `false`), labelled `wrong_format`. The retry mechanism was barely exercised: no step needed a retry in the official run, and one step in a repeat run was retried after an empty output.

## Limitations

- Extra API calls and time per run.
- Small benchmark (10 tasks, one official run); results may not generalise, and a gain of two tasks is within run-to-run variation.
- Checks are programmatic and can be wrong; the verifier is a small model and can pass a wrong answer that is well formed.
- Free-tier rate limits slow long runs.

## What we built vs what we reused

Built by the team: the splitter, runner, checker, caching and provider switch; the benchmark, scorer and dataset; the linter, web pages and docs.
Reused: google-genai, python-dotenv, PyYAML, pytest and Flask, the Gemma 4 model through the Gemini API, and the Agent Skill format.

## Open source and dataset

Public repo with an open license: https://github.com/Yasaswini-ch/skill-compiler. The failure dataset and its card are in [`benchmark/dataset/`](../benchmark/dataset/) and [`benchmark/DATASET_CARD.md`](../benchmark/DATASET_CARD.md). Anyone can add a failure with the "Submit a failure" issue form.
